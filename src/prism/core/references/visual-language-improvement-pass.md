# Visual language improvement pass

Run this compulsory pass after constructing a wireframe and before the final rendered inspection and delivery. Its purpose is to make information easier to understand at a glance—not to add decoration, increase fidelity indiscriminately, or restyle the product.

## Review every screen

Inspect every created screen and state in journey order. For each one, ask:

1. **Decision:** Is the main answer, comparison, risk, saving, or next action clear within the first scan?
2. **Information shape:** Is information presented in the form that best supports the task—comparison, grouped facts, proof, progress, choice, or explanation—rather than as an undifferentiated text block?
3. **Hierarchy:** Do title, supporting reason, primary facts, proof, exceptions, and actions have a clear reading order?
4. **Component expression:** Does the layout use documented Tata 1mg Dopamine components and the correct list, card, divider, sheet, or action-bar structure?
5. **Consistency:** Does a useful pattern established on one screen carry through equivalent screens in the same task?
6. **Restraint:** Does the change preserve the agreed UX, content truth, user safety, and the coral/orange constraint?

Improve only issues that materially reduce comprehension, comparison, confidence, or action clarity. Do not add visual treatment merely to make a screen look more designed.

## When information needs a stronger structure

Select the smallest pattern that makes the information intelligible:

| User need | Preferred visual treatment |
| --- | --- |
| Compare two named choices | Two clearly labelled, balanced comparison units; place the meaningful difference near the top |
| Establish that a replacement is safe or equivalent | A compact shared-facts block, visible matching criteria, and concise expert/provenance proof |
| Explain a price difference | Make the saving explicit; use a short expandable “why” explanation rather than a long up-front paragraph |
| Build confidence before a consequential action | Ordered proof points with clear source/actor, consequence, and recovery where relevant |
| Scan several facts about one object | Group related facts, align labels and values, and use dividers or a documented surface only where they improve scanning |
| Show a choice with a recommended option | Give the recommendation clear rationale and hierarchy, while preserving the alternative and its outcome |

For an equivalent-medicine bottom sheet, a strong pattern is: a clear thesis (for example, same salt/lower price), two labelled medicine summaries, a compact shared-comparison block, pharmacy or prescription proof, an optional “why” disclosure, then one primary action and a clear keep-current option. Use this pattern only when the facts and user decision genuinely match it.

Do not turn every fact group into a card. Cards should represent independent objects or choices; use alignment, spacing, headings, and Dividers for facts that belong to one scan.

## Targeted visual research

Load `local-inspiration-reference-pass.md` and the bundled `../skills/mobbin-visual-pattern-research/SKILL.md` for every completed wireframe. Together they inventory every meaningful element across every screen and state, consider an alternative for each, and search for analogous comparison, choice, explanation, proof, status, action, or component patterns—not necessarily the exact domain scenario—before returning a visual composition brief for each screen.

Search the curated local library by user job, information shape, state, and unresolved element. Inspect no more than five actual images and retain no more than three useful references. Use those references as calibrated evidence of visual structure and taste. If no credible local analogue exists, record “no local fit” rather than forcing a match.

Reuse relevant selected screens from the pre-wireframe Mobbin Reference Pass when they already answer an element’s visual question. Otherwise, use the specialist skill’s intent-to-element search ladder, grouping only genuinely equivalent repeated elements. Adapt only the structural lesson through the local Tata 1mg Dopamine system. Carry only the distilled visual insight across screens in the current wireframe task; do not turn one external example into a permanent design-system rule.

## Revise and verify

After the review, revise the artifact where needed and inspect the rendered result again. Confirm that each screen:

- communicates its decision and main action at a glance;
- represents complex information with an appropriate structure rather than a text dump;
- retains accurate content, requirements, and recovery paths;
- preserves component anatomy, accessibility, and source/product continuity;
- has no accidental clipping, dense unscannable blocks, competing actions, or decorative coral/orange surface use.
- has an explicit internal adopt, adapt, or retain decision for every meaningful element.

In the final Design Notes, include a concise **Visual language improvements** bullet only when this pass materially changed the wireframe. State what was clarified and why; do not provide a process transcript.
